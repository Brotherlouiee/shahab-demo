# استاندارد تدوین و نگهداری اسناد پروژه

> **وضعیت:** لازم‌الاجرا برای اسناد تازه و هر سندی که واقعاً بازبینی یا تغییر می‌شود  
> **تاریخ:** ۲۰۲۶-۱۰-۲۵  
> **مالک محتوا:** مالک پروژهٔ شهاب  
> **مرجع بالادست:** AGENTS.md و پروتکل اجرای تسک  
> **دامنه:** آزمون کیفیت اسناد فنی، اجرایی، معماری، وضعیت، handoff و تصمیم‌های پروژه

## هدف

این فایل چک‌لیست آزمون اسناد است، نه مجوز بازنویسی همهٔ تاریخچه. پیش از push یا PR مستنداتی، آزمون‌های بخش «دروازهٔ پذیرش سند» را روی فایل‌های تازه و فایل‌هایی که در همان تغییر دست‌کاری شده‌اند اجرا و نتیجه را ثبت کن. سند تاریخیِ نامرتبط را برای هماهنگی ظاهری تغییر نده.

## اطلاعات لازم

در سند تازه یا بازنویسی اساسی، موارد مرتبط زیر باید روشن باشند:

- هدف و مخاطب سند؛
- وضعیت آن، مانند پیش‌نویس، مصوب، جاری، تاریخی، موکول یا بازنشسته؛
- مالک محتوا و تاریخ آخرین بازبینی؛
- دامنه و مرزهای بیرونی؛
- مرجع بالادست و منبع هر ادعای مهم.

برای اصلاح کوچک، افزودن metadata بی‌ربط لازم نیست؛ اما وضعیت یا مرجع حقیقت نباید مبهم بماند.

## دروازهٔ پذیرش سند

پیش از ارسال هر تغییر مستنداتی، هر مورد را **قبول، رد یا نامرتبط با دلیل** ثبت کن:

| آزمون | شرط قبولی |
| --- | --- |
| هدف و مرز | خواننده می‌تواند بگوید سند برای چیست و چه چیزی را پوشش نمی‌دهد. |
| وضعیت تصمیم | واقعیت، تصمیم تأییدشده، پیشنهاد و پرسش باز از هم قابل تشخیص‌اند. |
| مالکیت مرجع | هر وضعیت یا قاعدهٔ جاری مرجع یگانه و مشخص دارد؛ تعارض جاری صفر است. |
| شواهد | همهٔ ادعاهای متغیرِ «انجام‌شده»، انتشار یا پذیرش به منبع قابل پیگیری وصل‌اند؛ مجهول حدس زده نمی‌شود. |
| طراحی تأییدنشده | هیچ قابلیت، معماری، فناوری، vendor، هزینه یا زمان‌بندیِ تأییدنشده به‌صورت الزام یا تصمیم قطعی نوشته نشده است. |
| مرزبندی فاز | شناسه‌ها، تسک‌ها، معوقات و معیارهای پذیرش یک فاز به فاز دیگر کپی نشده‌اند، مگر با تصمیم صریح مالک. |
| اثر و Done | برای برنامه یا تغییر، نتیجهٔ قابل مشاهده و شاهد لازم روشن است؛ CI، merge و deploy به‌جای هم استفاده نمی‌شوند. |
| اصول و رترو | نیاز به قرارداد پیش از UI، حفظ رفتار، دامنهٔ MVP، پرهیز از فناوری/خدمت غیرضروری، تعداد PR متناسب و آزمون نزدیک رعایت شده‌اند؛ موارد خارج از اختیار به مالک ارجاع شده‌اند. |
| پیوندها | همهٔ مسیرها، شناسه‌ها و لینک‌های افزوده یا تغییرکرده در دامنهٔ تغییر معتبرند. |
| محرمانگی | secret، کلید، token، رمز، DSN، دادهٔ شخصی یا جزئیات محیط خصوصی در متن عمومی وجود ندارد. |
| دامنهٔ تغییر | فقط فایل‌های لازم برای یک تصمیم یا تحویل منسجم تغییر کرده‌اند؛ بازنویسی جمعیِ نامرتبط صفر است. |
| ثبت تغییر | CHANGELOG و توضیح PR متناسب با اثر واقعی‌اند و همهٔ خطوط توضیح PR با واژهٔ فارسی آغاز می‌شوند تا راست‌چین حفظ شود. |

اگر آزمونی رد شد، سند تا رفع آن آمادهٔ بازبینی/ادغام نیست. اگر پاسخ به طراحی محصولی، هزینه، دسترسی یا تغییر بیرونی وابسته است، آن مورد را با شاهد، اثر و گزینهٔ پیشنهادی برای مالک ثبت کن؛ حدس نزن و کار مستقل و امن را بی‌دلیل متوقف نکن.

## وضعیت‌ها و شواهد

- **انجام‌شده:** برای نرم‌افزار، نتیجهٔ آزمون یا پذیرش ثبت شود؛ PR مرج‌شده به‌تنهایی کافی نیست. نتیجهٔ production جداگانه ذکر شود.
- **باز:** معیار یا شاهد باقی‌مانده روشن باشد.
- **موکول:** دلیل و شرط بازنگری ثبت شود؛ با حذف یا انجام‌شدن یکی نیست.
- **نامعلوم:** اطلاعات کافی برای نتیجه‌گیری وجود ندارد؛ از زبان قطعی استفاده نکن.
- **تاریخی:** تاریخ و زمینه حفظ شود؛ «گام بعدی» قدیمی به‌تنهایی دستور امروز نیست.

## روال تغییر مستندات

1. منبع حقیقت و فایل‌های واقعاً مرتبط را بخوان.
2. مالک موضوع را مشخص کن و همان مرجع را تغییر بده.
3. کوچک‌ترین تغییر سازگار را انجام بده؛ سند نامرتبط را تازه‌سازی صوری نکن.
4. تعارض جاری را برطرف کن یا برای تصمیم مالک گزارش بده.
5. آزمون‌های پذیرش سند را اجرا و لینک‌ها را بررسی کن.
6. وضعیت آزمون محلی، CI، merge، استقرار و پذیرش را جدا گزارش کن.
7. محتوای قابل انتشار را از نظر محرمانگی مرور کن.
8. CHANGELOG را فقط به اندازهٔ اثر واقعی تغییر بده.

## استفاده از درس‌های رترو

این قواعد باید به شکل آزمون سند اجرا شوند، نه شعار یا الزام فناوری خاص:

- اگر سند دربارهٔ قابلیت کاربری است، روشن باشد قرارداد، داده و مالکیت وضعیت پیش از طراحی UI کجا تعیین می‌شوند.
- اگر سند refactor را تعریف می‌کند، خط مبنا و شیوهٔ اثبات حفظ رفتار را مشخص کند.
- هر سرویس، dependency، زیرساخت، دروازه یا PR تازه باید دلیل مرتبط با نیاز و معیار پذیرش داشته باشد.
- تغییرهای دارای هدف و آزمون مشترک در یک PR منسجم بمانند؛ تغییرهای نامرتبط در یک PR ادغام نشوند.
- آزمون‌های نزدیک و شواهد قبلیِ معتبر اولویت دارند؛ تکرار آزمون باید علت داشته باشد.
- تصمیم‌های معمول فنی موجب توقف و سؤال بی‌دلیل نشوند؛ سؤال برای تصمیم مالک، هزینه/دسترسی تازه یا اثر بیرونی لازم است.
- نتیجهٔ نهایی باید کار انجام‌شده، شاهد، محدودیت و مورد باز را تفکیک کند.

## بازبینی متناسب

سند فعال با تغییر مرجع بالادست، پایان milestone یا استفادهٔ مجدد از handoff بازبینی شود؛ بازبینی تقویمی حداکثر هر ۹۰ روز کافی است. سند تاریخی تا وقتی نیاز واقعی به تغییرش نیست دست‌نخورده بماند.
