# پروتکل اجرای دقیق و کم‌اتلاف تسک‌ها

نسخه: ۱.۰ — ۲۰۲۶-۱۰-۱۰

## جایگاه و الزام

این سند برای هر تسک توسعه، اصلاح، تست، migration و مستندسازی پروژه لازم‌الاجرا است. پیش از تغییر، آن را همراه قواعد فعال و سند جامع بخوان. این پروتکل مکمل سه قانون طلایی، سند جامع و همکاری ایمن Git و IDE است؛ هیچ الزام امنیتی، تست، خواندن منابع یا gate مصوب را حذف نمی‌کند. دستور صریح مالک محصول مقدم است؛ تعارض واقعی را مستند کن و بی‌صدا دور نزن.

هدف: حذف کاوش، اجرای تست و رفت‌وبرگشت غیرضروری، بدون کاهش کیفیت، امنیت یا سلامت داده. سرعت با حذف کار تکراری به دست می‌آید، نه پنهان‌کردن خطا.

## ۱. تعیین محدوده پیش از پیاده‌سازی

ابتدا وضعیت Git، قواعد فعال، قرارداد موجود و معیار پذیرش را بررسی کن. تغییرات محلی متعلق به کاربر را حفظ کن؛ branch یا worktree مناسب را مطابق قواعد همکاری انتخاب کن. مستقیم روی main کار نکن و بازنویسی تاریخچه یا force-push انجام نده.

پس از خواندن منابع الزامی، کاوش کد را محدود نگه دار: ابتدا rg و فهرست فایل‌ها، سپس فایل‌های مربوط. جست‌وجوی مستقل را می‌توان موازی اجرا کرد؛ تغییرات وابسته و عملیات Git باید با ترتیب معتبر انجام شوند.

پیش از اولین تغییر، در checkpoint یا یادداشت اجرای تسک این موارد را کوتاه ثبت کن:

| مورد | پرسش لازم |
|---|---|
| رفتار فعلی و مطلوب | محرک دقیق چیست و خروجی قبل/بعد چه تفاوتی دارد؟ |
| مرز تغییر | UI، قرارداد API، نشست، مالکیت، دیتابیس، داده یا scoring؟ |
| وابستگی | چه فراخواننده‌ها، routeها، stateها، تست‌ها و fixtureهایی این رفتار را فرض کرده‌اند؟ |
| محیط آزمون | کدام suite وابستگی لازم را واقعاً دارد و چگونه آماده می‌شود؟ |
| حداقل اثبات | کدام بررسی، معیار پذیرش را با نتیجهٔ قابل مشاهده ثابت می‌کند؟ |
| خطر | آیا مسیرهای مجاور، دادهٔ موجود، امنیت یا طراحی مصوب ممکن است تغییر کنند؟ |

کامپوننت/asset/راهکار موجود را پیش از ساخت نسخهٔ جدید پیدا کن. refactor، dependency جدید، تغییر طراحی یا گسترش دامنهٔ فرضی به تسک اضافه نکن.

## ۲. نقشهٔ آزمون متناسب با اثر تغییر

انتخاب suite را از روی فرمان، config و fixture واقعی انجام بده؛ نام تست یا پوشه به‌تنهایی کافی نیست. پیش از اجرای تست، نیاز به API، PostgreSQL، catalogue، migration، مرورگر، proxy، cookie و احراز هویت را مشخص کن. backend یا دادهٔ لازم را صرفاً فرض نکن.

| تغییر | اثبات نزدیک مناسب |
|---|---|
| فاصله، رنگ یا هندسه | همان صفحه و viewport مرجع؛ اندازه‌گیری یا تصویر لازم؛ مسیر مجاورِ تحت اثر CSS مشترک |
| تعامل UI یا ناوبری | حالت قبل/بعد، لغو/تأیید، Back و تست‌های وابسته به رفتار سابق |
| API یا قرارداد پاسخ | schema، موفقیت، خطای مرتبط و سازگاری مصرف‌کننده |
| نشست، احراز هویت یا مالکیت | محیط واقعی لازم؛ نشست معتبر/نامعتبر، خروج و جلوگیری از دسترسی حساب دیگر |
| ذخیره‌سازی یا migration | PostgreSQL در موارد الزام‌شده؛ transaction، rollback، idempotency و حفظ دادهٔ قبلی |
| موتور یا داده | منابع مصوب، fixture/golden مرتبط و invariants بدون تغییر خاموش ضرایب |

این جدول جایگزین gateهای اجباری پروژه نیست. full suite را طبق الزام مصوب یا به دلیل دامنهٔ اثر مشخص اجرا کن؛ علت اجرای اضافی را ثبت کن. نبود محیط مناسب را با mock کردن مسیری که باید واقعی آزموده شود جبران نکن. mock برای آزمون قرارداد مجاز است، اما اثبات اتصال واقعی نیست.

نمونه: تأیید خروج باید تست‌های فرض‌کنندهٔ خروج فوری را نیز اصلاح کند. آزمون 204 خروج واقعی در suite دارای backend اجرا می‌شود؛ suite عمومی بدون backend محل مناسب این اثبات نیست.

## ۳. پیاده‌سازی و آزمون نزدیک

کد و تست‌های وابسته به تغییر عمدی رفتار را در همان چرخه اصلاح کن. کوچک‌ترین patch سازگار را بساز؛ آزمونی اضافه کن که خطای واقعی یا معیار پذیرش را بررسی کند، نه صرفاً ساختار پیاده‌سازی را تکرار کند.

برای هر آزمون، فرمان، محیط، revision یا وضعیت کد و نتیجه را ثبت کن. پس از موفقیت، آن را بدون تغییر مرتبط، تغییر محیط یا نگرانی جدید تکرار نکن. اگر کد بعداً تغییر کرد، آزمون مرتبط دیگر اثبات نسخهٔ نهایی نیست و باید تکرار شود.

خطای وابستگی یا آماده‌سازی را از شکست محصول جدا کن. پیش از بازسازی node_modules، نصب مجدد یا تغییر محیط، علت و حداقل اقدام لازم را مشخص کن. lockfile یا نسخه‌ها را برای درمان حدسی تغییر نده. دیتابیس، volume و دادهٔ کاربر را reset یا حذف نکن.

## ۴. gate پیش از اولین push

- برای هر تغییر مستنداتی، [استاندارد تدوین و نگهداری اسناد](DOCUMENTATION_STANDARDS.md) را اجرا کن؛ هدف، شاهد، وضعیت، پیوندها، مرجع حقیقت و ایمنی انتشار را بررسی کن. این کنترل مجوز بازنویسی اسناد نامرتبط نیست.

- diff و فهرست فایل‌ها را بررسی کن: فقط محدودهٔ مجاز، بدون secret و تغییر نامرتبط.
- فراخواننده‌ها، تست‌ها و fixtureهای رفتار قدیمی را دوباره با جست‌وجوی هدفمند بررسی کن.
- تست‌های هدفمند لازم و بررسی‌های الزامی قابل اجرا را روی تغییر نهایی اجرا کن.
- هر بررسی اجرا نشده را با علت و محل اجرای بعدی مشخص کن؛ «اجرا نشده» را موفق گزارش نکن.
- مستندات و CHANGELOG را فقط به اندازهٔ اثر واقعی تغییر به‌روز کن؛ سند تداوم طبق قاعدهٔ داستان یا دستور صریح مالک.
- commit کامل و قابل بازبینی بساز و فقط فایل‌های مقصود را stage کن.

اگر محیط محلی واقعاً قادر به بررسی لازم نیست، از محیط CI مصوب استفاده کن و محدودیت را گزارش بده؛ شرط ناممکن نساز و task را با وعدهٔ ادامه رها نکن.

## ۵. تشخیص شکست CI پیش از اصلاح

۱. SHA و attempt اجرا را با آخرین commit تطبیق بده.
۲. job، step و اولین خطای مؤثر را از خروجی همان اجرا بخوان؛ پیام کلی failed کافی نیست.
۳. شکست را طبقه‌بندی کن: محصول/قرارداد، انتظار قدیمی تست، fixture، آماده‌سازی محیط، dependency، ناپایداری آزمون یا سرویس خارجی.
۴. یک فرضیهٔ مشخص همراه شاهد و اقدام اصلاحی حداقلی ثبت کن.
۵. همان مسیر را در نزدیک‌ترین محیط معتبر بازتولید یا بررسی کن؛ سپس اصلاح کن.
۶. تست نزدیک را اجرا کن و تنها بعد از شواهد معتبر push کن.

rerun بدون تغییر فقط برای شواهد خرابی موقت محیط یا سرویس قابل توجیه است؛ علت را ثبت کن. برای خطای یکسان، push یا rerun حدسی پشت‌سرهم نکن؛ فرضیه و شواهد را بازبینی کن.

تست، assertion، timeout، کنترل مالکیت یا امنیت را صرفاً برای سبزشدن CI حذف/شل/skip نکن. اصلاح انتظار تست فقط وقتی مجاز است که رفتار جدید عمداً تأیید شده باشد و تست هنوز موفقیت و شکست مربوط را اثبات کند. افزایش timeout فقط با علت اندازه‌گیری‌شده، نه پنهان‌کردن hang.

## ۶. ثبت زمان از شروع

از شروع واقعی تسک زمان را ثبت کن؛ اگر ثبت دیر آغاز شد، بخش قبلی را «ثبت نشده» بنویس. ایجاد branch یا timestamp commit فقط رخداد Git است و جایگزین زمان فعالیت نیست.

بخش‌ها: خواندن قواعد/اسناد و بررسی، پیاده‌سازی، تست/build، رفع خطا و تکرار بررسی، مستندات/Git/PR، انتظار ابزار/CI/ورودی ضروری.

زمان کل دیواری را از مدت فعالیت‌ها جدا کن. کارهای موازی را دوباره در مجموع نشمار؛ زمان انتظار با کاری که هم‌زمان انجام شده قابل جمع ساده نیست. ساعت و timezone، شروع/پایان و علت تکرار را ثبت کن. ابزار زمان‌سنج سبک کافی است؛ این ثبت نباید به فعالیت اصلی یا گزارش‌های مکرر تبدیل شود. مصرف توکن فقط با آمار واقعی گزارش شود.

## ۷. شرط تحویل و گزارش نهایی

تحویل شامل رفتار تأییدشده، بررسی‌های لازم روی revision نهایی، مستندات متناسب و PR قابل بازبینی است. merge و deploy فقط با مجوز مربوط انجام می‌شوند. موفقیت CI به معنای deploy یا پذیرش بصری مستقل نیست.

گزارش کوتاه نهایی:
- نتیجه و علت واقعی مشکل؛
- تست/فرمان، محیط و نتیجه، SHA نهایی و وضعیت CI؛
- بررسی‌های اجرا نشده و محدودیت واقعی؛
- جدول زمان شامل مدت، کار و علت تکرار، با تفکیک «ثبت نشده»؛
- حداکثر سه عامل اصلی اتلاف و اقدام مشخص برای تسک بعدی.

برای تغییر کوچک، همین پروتکل را کوتاه اجرا کن؛ سند بلند، تست اضافی یا refactor برای اثبات رعایت پروتکل نساز. برای مانع واقعی، کار مستقل ممکن را تکمیل کن و شاهد و اقدام ضروری را دقیق اعلام کن.
