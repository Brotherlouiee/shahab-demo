# قرارداد اجرایی برنامه‌ریزی فاز پنجم شهاب

## هدف و وضعیت

فاز پنجم فقط دو کارکرد اصلی دارد: (۱) ساخت برنامهٔ اولیهٔ توسعه در چرخه‌های هفتگی و (۲) بازچینی برنامه با درخواست مالک یا تغییر شواهد و شرایط اجرا. معماری ابزار با تصمیم مصوب P5-D14 یک Skill واحد Codex به نام `shahab-planner` است؛ قالب برنامه JSON مرجع و نمایش انسانی در پاسخ Skill است. این مصوبه و مصوبات D01/D02 به‌تنهایی تأیید کل قرارداد نیستند؛ وضعیت قرارداد کلی در صورت نیاز به تأیید جداگانهٔ مالک `PENDING_OWNER_APPROVAL` می‌ماند.

Skill چهار درخواست را با یک ورودی مشخص می‌پذیرد: `INITIAL PLAN`، `REPLAN`، `VALIDATE` و `EXPLAIN`. هر چهار رفتار از همان قرارداد، منابع و کنترل‌ها استفاده می‌کنند؛ چهار موتور، سرویس یا جریان دادهٔ مستقل ساخته نمی‌شود.

`MAX_IMPLEMENTATION_TIME = 60 MINUTES` برای طراحی حداقلی، ساخت، آزمون‌های ضروری و اصلاح Skill و هر اسکریپت کوچک اعتبارسنجی است. این زمان با اجرای برنامه‌ریزی واقعی اولیه جداست. اگر پیاده‌سازی از سقف عبور کند، دامنهٔ ابزار کوچک می‌شود؛ سقف افزایش نمی‌یابد و کار ضروری به مأموریت دیگری منتقل نمی‌شود.

## ورودی‌های مرجع و حدود اختیار

منابع روایی و مصنوعات گواهی‌شدهٔ فاز چهارم از نسخه‌های ثبت‌شده در `source-reading-coverage.csv`، `planning-knowledge-registry.json` و `phase4-artifact-consumption.csv` خوانده می‌شوند. داده‌های Phase 4 فقط مرجع خواندنی‌اند. Snapshot، Mapping، Overlay، Ledger و گراف ترکیبی فاز چهارم نباید با برنامه‌ریزی تغییر کنند. گراف یا Ledger تکراری برای فاز پنجم ساخته نمی‌شود.

سندهای حاکم و مصوبات ثبت‌شده در `source-policy-trace.csv` مرجع سیاست هستند. برنامه می‌تواند کار و ترتیب را پیشنهاد کند، اما سیاست محصول، وضعیت حقوقی/مالی، مجوز انتشار یا تصمیم مالک را تغییر نمی‌دهد. مقدار نامعلوم با `UNKNOWN` ثبت می‌شود؛ UNKNOWN صفر، برآورد یا مجوز تلقی نمی‌شود.

محدودیت‌های مشخص Snapshot نیز در برنامه‌ریزی حفظ می‌شوند: دو الزام `AO:BP-C-0419:01` و `AO:BP-C-0236:08` پوشش اجرایی تأییدشده ندارند و در صورت اثر بر outcome، باید آشکار و مسدودکننده بمانند؛ نبود رابطهٔ `PARALLEL_SAFE` مجوز اجرای موازی نیست. handoffهای C05A→R02 و H04:003 فقط در دامنهٔ Package ثبت شده‌اند و Task یا تقدم تازه از آن‌ها استنتاج نمی‌شود؛ تا روشن شدن قرارداد لازم، تعهد وابسته ممکن نیست. رابطه‌های سریال‌شدهٔ Overlay معادل تعداد وابستگی‌های معنایی مستقل نیستند. اختلاف خلاصه‌های تاریخی C11b/C12a/R03/R08 با شمار ریزکارهای ثبت‌شده، در یادداشت‌های گراف حل و مستند شده است و کار ممیزی جدید یا تغییر Snapshot ایجاد نمی‌کند (`PHASE_4_COMBINED_GRAPH_UNDERSTANDING.md` §§2–5، 6؛ Snapshot و Manifest همان نسخهٔ گواهی‌شده می‌مانند).

## مدل تحویل‌دادنی و تخصیص کار — مصوبهٔ مالک دربارهٔ D01 و D02

مالک در 2026-11-28 گزینهٔ C را برای هر دو تصمیم به‌صورت مشترک تصویب کرد: Deliverable مبتنی بر outcome و تخصیص مختلط به کوچک‌ترین واحد کاریِ مستقل و قابل‌تخمین. این دو مصوبه در `decision-register.json` با شاهد صریح مالک ثبت شده‌اند؛ تصویب آن‌ها به معنی تأیید کل قرارداد یا تصویب تصمیم دیگری نیست. قواعد اجرایی مصوب عبارت‌اند از:

1. واحد برنامه‌ریزی هفتگی، Deliverable مبتنی بر outcome است.
2. هر Deliverable نتیجه‌ای مشخص، قابل استفاده یا قابل آزمون دارد و همچنان تابع تعریف مصوب خروجی قابل استفاده و یکپارچه است.
3. یک Deliverable می‌تواند Taskها و Subtaskهایی از بسته‌های مختلف را دربر بگیرد.
4. کوچک‌ترین واحد مستقل و قابل‌تخمین مبنای تخصیص است؛ بسته به مورد Task یا Subtask.
5. Task والد و Subtaskهای تخصیص‌یافتهٔ آن هم‌زمان تلاش مستقل محسوب نمی‌شوند و دوباره‌شماری ندارند.
6. شناسه‌های اصلی گراف حفظ می‌شوند؛ Skill شناسهٔ کاری موازی نمی‌سازد.
7. کار زیرساختی به Deliverable دارای مصرف‌کنندهٔ واقعی متصل می‌شود، مگر استثنای ضروری و مستندی که سیاست مصوب اجازه دهد.
8. تشکیل Deliverable تابع وابستگی، ظرفیت، معیار پذیرش و سقف چرخهٔ هفت‌روزه است.
9. با درخواست تغییر اولویت، Skill می‌تواند ترکیب و ترتیب Deliverableهای پیشنهادی را بازبینی کند؛ قیود hard-order و مجوزهای تعهد همچنان برقرارند.

## دادهٔ حداقلی هر برنامه

یک برنامهٔ قابل بازبینی باید در یک خروجی نسخه‌پذیر ثبت کند:

| داده | قاعده |
| --- | --- |
| Week ID و بازه | هر چرخه حداکثر ۷ روز تقویمی است؛ زمان آغاز/پایان و مبنای هفته مشخص باشد. |
| Deliverable ID و outcome | خروجی باید نتیجهٔ قابل استفاده/آزمون را بیان کند؛ Task فنی به‌تنهایی بدون دلیل، تحویل‌دادنی محصول نیست. |
| Work node references | ارجاع دقیق به Task/Subtask یا منبع کار؛ وضعیت منبع حفظ شود. کار یک بار تخصیص و محاسبه شود؛ والد و فرزند با هم دوباره‌شماری نشوند. |
| Dependencies | تقدم سخت، وابستگی قراردادی، ورودی/شاهد و رابطهٔ صرفاً اطلاعاتی از هم جدا بمانند؛ فقط تقدم معتبر ترتیب اجرا را محدود می‌کند. |
| Applicable policies | شناسه و محل منبع سیاست‌های مرتبط، از جمله مرحله، امنیت، مالی، پذیرش و انتشار. |
| Open decision blockers | شناسهٔ تصمیم واقعاً باز، دامنهٔ اثر، شرط مسدودکننده و مالک؛ فقط کار متأثر مسدود می‌شود. |
| Effort estimate و required capacity | نوع، واحد، بازه/مقدار، دوره، منبع و عدم‌قطعیت؛ ظرفیت واقعی از فرض جدا و پیش از تعهد تأیید شود. |
| Development cost و operating cost | جداگانه، با واحد پول/دوره، منبع و حالت اطمینان؛ هیچ‌کدام از دیگری استنتاج نشود. |
| Token estimate | در صورت کاربرد، مدل/نسخه، واحد و منبع؛ هزینهٔ توکن از سایر هزینه‌ها جدا باشد. |
| Acceptance criteria و test references | نتیجه، شرط، روش مشاهده و شاهد آزمون/بازبینی قابل ارجاع؛ معیارهای محصول از آمادگی انتشار جدا باشند. |
| Status و planning evidence | وضعیت چرخهٔ برنامه، دلیل و شواهد منبع؛ برآورد، اندازه‌گیری، آزمون و تأیید از هم متمایز باشند. |

اگر داده‌ای برای برنامه‌ریزی اولیه هنوز موجود نیست، `UNKNOWN` و اثر آن بر امکان تعهد ثبت می‌شود. تعهد هفتگی مستلزم برآورد معتبر تلاش/زمان/هزینه/توکنِ مرتبط، ظرفیت تأییدشده، وابستگی‌های آماده، معیار پذیرش و اختیار صریح مالک است. UNKNOWN را نمی‌توان با صفر یا فرض پنهان جایگزین کرد. هزینهٔ توسعه، بهره‌برداری، ابزار و توکن جدا می‌مانند. نسبت‌های Discovery/Delivery مصوب O5-09 حفظ می‌شوند؛ ۸۰/۲۰ مبنا، ۹۰/۱۰ برای کار بحرانی و ۷۰/۳۰ برای کار نامطمئن با timebox است. این نسبت‌ها مقدار ظرفیت واقعی یا تعداد نیرو را تعیین نمی‌کنند.

هر چرخه حداکثر هفت روز تقویمی است. کار بزرگ باید به outcomeهای کوچک و قابل آزمون شکسته شود. استثنای چندچرخه‌ای فقط با کنترل‌های ثبت‌شدهٔ موجود ممکن است: دلیل تقسیم‌ناپذیری ایمن، گزینه‌های تقسیم و علت رد، وابستگی‌ها، سقف کل زمان و هزینهٔ توسعه/بهره‌برداری با تأیید مالک، خروجی میانی و oracle آزمون برای هر چرخه، تاریخ بازبینی و reconciliation تخصیص برای جلوگیری از دوباره‌شماری. استثنا، چرخهٔ بیش از هفت روز یا انتشار خودکار ایجاد نمی‌کند. گیت‌های پذیرش و انتشار مصوب O5-10/RG/REL و کنترل‌های مالی و امنیتی برقرار می‌مانند. پایان یک هفته یا مرحله، به‌تنهایی مجوز انتشار، فعال‌سازی مالی یا تکمیل محصول نیست.

## اولویت، ترتیب و بازبرنامه‌ریزی

ابتدا قیود سخت و آمادگی اجرا بررسی می‌شوند: مجوزها و سیاست‌های امنیتی/مالی، `HARD_ORDER`، آمادگی قرارداد موردنیاز، وابستگی‌ها، ظرفیت و تصمیم باز در دامنهٔ واقعی اثرش. سپس گزینه‌های امکان‌پذیر با شواهد و عدم‌قطعیت به مالک نشان داده می‌شوند تا اولویت را تعیین کند. هیچ امتیاز یا ارزش ادعایی قید سخت را جبران نمی‌کند. وزن‌دهی، WSJF یا الگوریتم بهینه‌سازی در MVP وجود ندارد.

تغییر اولویت درخواستی مالک به‌تنهایی دامنهٔ مصوب را حذف نمی‌کند، `HARD_ORDER` را نقض نمی‌کند، قرارداد وابسته را آماده نمی‌سازد، تصمیم باز را حل نمی‌کند و مجوز انتشار یا فعال‌سازی مالی نیست. Skill اثر درخواست را روی outcomeها، تقدم‌ها، ظرفیت، برآوردها، معیارهای پذیرش و گیت‌ها مشخص می‌کند. اگر تغییر ممکن نباشد، تعارض و گزینه‌های شدنی را گزارش می‌کند. برنامهٔ پیشنهادی جدید باید تفاوت نسخهٔ فعلی و پیشنهادی، علت، شواهد و اثر را آشکار سازد. برنامهٔ متعهدشده بدون مجوز صریح مالک تغییر نمی‌کند؛ تاریخچه با Git نگهداری می‌شود.

## معماری حداقلی و سقف ساخت

معماری مصوب D14 این است: یک Skill متنی `shahab-planner`، یک فایل JSON مرجع برنامه در `docs/phase5/weekly-plan.json`، نمایش خوانا در پاسخ Skill، تاریخچه با Git و یک اسکریپت کوچک Python اعتبارسنجی در `scripts/validate_plan.py` داخل Skill. این مسیرها ساختار آینده‌اند و در این مأموریت هیچ‌کدام ایجاد نمی‌شوند. اسکریپت فقط JSON، یکتایی Deliverable ID، اعتبار Task/Subtask reference، تخصیص تکراری و والد/فرزند، تقدم `HARD_ORDER` معتبر، چرخهٔ حداکثر هفت‌روزه، سازگاری واحدهای ظرفیت، blocker تصمیم باز، UNKNOWN مؤثر بر تعهد و وجود شواهد ضروری را به‌صورت قطعی کنترل می‌کند؛ موتور زمان‌بندی، اولویت، تخمین یا داوری معنایی نیست. ارزیابی outcome، کفایت شواهد، کیفیت تخمین و انطباق سیاستی بر عهدهٔ Skill و بازبینی مالک می‌ماند. دیتابیس، API، UI، داشبورد، وابستگی نرم‌افزاری تازه، گراف تکراری، سیستم مستقل نسخه و موتورهای مستقل از دامنه خارج‌اند.

مصوبهٔ اجرایی D14، به‌صورت یکپارچه:

1. ابزار یک Skill واحد Codex با نام `shahab-planner` است.
2. JSON تنها مرجع ذخیره‌شدهٔ برنامه است؛ فایل Markdown موازی یا مرجع مستقل دیگری ساخته نمی‌شود.
3. مالک برنامه را از پاسخ خوانای Skill می‌بیند و مجبور به مطالعهٔ مستقیم JSON نیست.
4. تاریخچهٔ نسخه‌ها با Git نگهداری می‌شود.
5. یک اسکریپت کوچک Python قواعد قطعی ضروری را می‌سنجد و به موتور برنامه‌ریزی/زمان‌بندی/اولویت/تخمین تبدیل نمی‌شود.
6. دیتابیس، API، UI، داشبورد، موتور مستقل، گراف تکراری، سامانهٔ نسخه یا dependency تازه ساخته نمی‌شود.
7. همان Skill چهار حالت `INITIAL PLAN`، `REPLAN`، `VALIDATE` و `EXPLAIN` و درخواست‌های نمایش/جزئیات/مقایسه را پوشش می‌دهد.
8. مجموع طراحی، ساخت، آزمون و اصلاح حداکثر ۶۰ دقیقه است؛ زمان اجرای برنامه‌ریزی اولیه جداست.
9. Skill بنا به درخواست جدول جامع، نمای هفتگی، جزئیات Deliverable و Task/Subtask، وابستگی، پذیرش، تخمین/ظرفیت/هزینه/توکن، مقایسهٔ نسخه و Gantt متنی ارائه می‌کند؛ دادهٔ نامعلوم `UNKNOWN` می‌ماند و نمایش چیزی اختراع نمی‌کند.

برای رعایت ۶۰ دقیقه، کارکرد ضروری محدود است به: خواندن مراجع موجود، ساخت پیشنهاد قابل بازبینی با چهار حالت، کنترل ارجاع/وابستگی/هفت‌روز/ظرفیت/UNKNOWN، ثبت diff در Git، و آزمون همین کنترل‌ها. هر نما، گزارش خودکار اضافی، الگوریتم امتیازدهی یا رابط مستقل اختیاری است و تا اثبات ضرورت وارد دامنه نمی‌شود. Validator قرارداد موجود مستقیماً برنامهٔ هفتگی را نمی‌خواند یا اعتبارسنجی نمی‌کند؛ بنابراین برآورد قبلیِ ۱۰ دقیقه برای اتصال آن، مبنای قابل اتکایی نیست. برآورد مشروط برای یک Skill با برنامهٔ JSON و فقط کنترل‌های قطعی لازم: طراحی/نگاشت ۷ دقیقه، ساخت دستورالعمل Skill و چهار رفتار ۱۷ دقیقه، اعتبارسنجی محلی حداقلی JSON و قیود برنامه ۲۰ دقیقه، آزمون رفتارهای ضروری و اصلاح ۱۱ دقیقه، حاشیه ۵ دقیقه؛ جمع ۶۰ دقیقه. این برآورد تنها با استفاده از Python و فایل‌های موجود، بدون نصب وابستگی، UI، renderer، schema framework یا قابلیت اضافی باورپذیر است و تضمین زمانی نیست. اگر کنترل‌ها در این دامنه نگنجند، جزئیات اختیاری حذف می‌شوند؛ قواعد مصوب محصول، سقف ۶۰ دقیقه و اعتبارسنجی لازم برای تعهد هفتگی تضعیف نمی‌شوند.
