# US-09.T07 — ممیزی مسیر سایت مستقر

یادداشت به‌روزرسانی: برنامه‌های authority سازمانی و دو اپراتور در بخش‌های نخست این checkpoint سابقهٔ بررسی‌اند. تصمیم نهایی مالک برای همین تحویل، مسیر تک‌مالکِ بخش «آماده‌سازی مسیر SSH محلی» و راهنمای پیوندشده است؛ کنترل دو نفره و MFA عملیاتی محقق نشده‌اند.

**وضعیت: معیار پایان محقق نشده است.** این checkpoint شواهد خواندنی و آزمون کوتاه مرورگر روی معماری موجود Docker/NGINX/آروان و `https://shahabfintech.ir` را ثبت می‌کند. مطابق تصمیم مالک، staging تازه، NetBird، آزمونگر دوم، Netlify، سرویس پولی، اسکن گسترده، آزمون بار و restart/restore روی production جزو این اجرا نیستند. آزمون معتبرِ PostgreSQL و ماندگاری PR #149 تکرار نشد. هیچ تغییر عملیاتی در سرویس، تنظیمات، کاتالوگ، volume یا image در production انجام نشد؛ آزمون مرورگر نشست و پاسخ‌های آزمایشی را از مسیر عادی کاربر ثبت کرد.

## آزمون کوتاه Chrome

- خانه در desktop و mobile با HTTP `200` و TLS معتبر باز شد. refresh مستقیم `/question/3`، `/loan-results` و `/loan-details` در هر دو viewport پاسخ `200` و صفحهٔ قابل‌نمایش داشت.
- در مسیر شخصیِ پرسشنامه، هر دو viewport از خانه به سؤال‌ها و سپس `/personal-info` رسیدند. POST ساخت نشست از API واقعی `201` و PUT پاسخ‌های ثبت‌شده `200` داد. این شواهد، frontend → API → ذخیرهٔ نشست/پاسخ در DB را برای همان درخواست‌ها ثابت می‌کنند؛ توصیهٔ موفق یا جزئیات وام را ثابت نمی‌کنند.
- بازکردن مستقل `/loan-results` بدون نشست معتبر، پیام «برای دیدن نتیجه، ابتدا پرسشنامه را در همین تب کامل کنید» و دکمهٔ شروع پرسشنامه را نشان داد؛ این حالت فاقد نتیجه با حالت موفق اشتباه نشد.
- مسیر مرورگر پیش از توصیه به `/personal-info` رسید. OTP واقعی خاموش است و در DB نیز serving/config فعال صفر است. بنابراین POST توصیهٔ موفق، بازکردن جزئیات همان وام، پروفایل، نشان‌ها، تاریخچه و خروج با حساب واقعی **اجرا نشدند**. ۲۰۰ بودن shell مسیرهای نتیجه و جزئیات، شاهد دادهٔ وام نیست. خطای توصیه با نشست کامل نیز اجرا نشد؛ وضعیت HTTP آن حدس زده نمی‌شود.

## برنامهٔ انتشار داده پیش از هر تغییر production

**این برنامه مجوز اجرا نیست.** مقصد فقط PostgreSQL موجود پروژهٔ `shahab-prod` است؛ migration فعلی head است و تکرار migration یا import قدیمی برنامه‌ریزی نمی‌شود. نامزدِ منبع رسمی موجود در `main@f9e0732` دارای SHA-256 منبع وام `598052635954071b192bb43505e572f30ee88efd99b4d5ae757f6d555bfaae45`، parser `loan-source.v1`، config `1.1.0`، کد عمومی مورد انتظار `official-598052635954-1.1.0` و ۱۰۲ ردیف است. این‌ها شواهد fixture/کد هستند، نه تأیید عملیاتی مالک برای production.

پیش از اقدام نوشتنی، مالک باید همین منبع/config و نسخهٔ مقصد را برای production تأیید کند؛ اپراتور باید backup سازگار و **بازیابی آزموده‌شده**، وضعیت دقیق دادهٔ موجود، روش دسترسی محدود، نقش‌های جداگانهٔ data-editor/admin و authority HTTPS با MFA را ارائه کند. تصویر فعلی ابزار محافظت‌شده را ندارد؛ اجرای artifact بازبینی‌شدهٔ آن در مسیر موردتأیید مالک باید ممکن شود، بدون انتشار خودسرانهٔ image یا سرویس تازه. سپس فقط با مجوز مستقل عملیات روی production، مسیر رسمی `import → review → prepare → approve → publish` اجرا و head، audit، ۱۰۲ عضو، config فعال و پاسخ API بازخوانی شود. هر خطا/نتیجهٔ نامعلوم پیش از retry با read-only audit بررسی شود.

بازگشت نسخه‌ای ابزار فقط به نسخهٔ قبلاً منتشرشده ممکن است؛ اکنون هیچ نسخهٔ فعالی وجود ندارد. بنابراین برای انتشار نخست، rollback نسخه‌ای به حالت خالی فراهم نیست. شکست پیش از commit باید به‌طور تراکنشی بی‌اثر بماند؛ اگر پس از انتشار مشکل کشف شد، ادامهٔ سرویس، انتشار اصلاحی یا بازیابی از backup همراه با حفظ/تطبیق نوشتن‌های کاربران، برنامه و مجوز جدا می‌خواهد. restore یا توقف production در این تسک انجام نشد. OTP واقعی نیز به تأیید قالب، کلید خصوصی و مجوز ارسال در تسک خودش وابسته است؛ mock روی production فعال نمی‌شود.

## نتیجه و اقدام لازم

معیار پایان T07، یعنی توصیهٔ واقعی و جزئیات همان وام روی سایت مستقر، هنوز محقق نشده است. برای گشودن مسیر انتشار، مالک باید **منبع/config نامزد بالا و روش محافظت‌شدهٔ اجرای ابزار روی زیرساخت موجود را مشخص و تأیید کند**؛ سپس برنامهٔ backup/بازگشت و مجوز دقیق import/publish جداگانه بررسی می‌شود. تا آن زمان هیچ انتشار داده، SMS، image، merge یا deploy انجام نمی‌شود. سند تداوم تا پایان واقعی User Story تغییر نمی‌کند.

زمان آغاز ممیزی ابزار در این نوبت `۲۰۲۶-۱۰-۲۲ ۰۷:۵۴ UTC` ثبت شد؛ تفکیک زمان مراحل پیش از این نقطه ثبت نشده و به‌عنوان اندازه‌گیری واقعی گزارش نمی‌شود. تأخیرهای مشاهده‌شده بیشتر از دسترسی شبکهٔ sandbox، راه‌اندازی Chrome و بررسی تطابق مسیرهای NGINX بود؛ آزمون‌های PR #149 بی‌دلیل تکرار نشدند.

## ادامهٔ T07 در PR #150 — تطبیق منبع و تمرین بازیابی

منبع خام `.agents/documents/دیتابیس وام های بانکی.unitext` در checkout بازبینی‌شدهٔ `main@f9e0732` با SHA-256 ثبت‌شده در `docs/source-integrity-verification.md`، یعنی `598052635954071b192bb43505e572f30ee88efd99b4d5ae757f6d555bfaae45`، یکسان است. `scripts.operations_tool.projection()` از همین فایل و قراردادهای مصوب ۱۰۲ ردیف، config `1.1.0`، `approved=true` و تصمیم‌های D-001 تا D-005 می‌سازد. این مسیر از fixture مستقل تست استفاده نمی‌کند. تأیید منبع در مخزن جای مجوز انتشار آن در production را نمی‌گیرد.

از PostgreSQL اصلی پروژهٔ `shahab-prod`، بدون توقف سرویس یا تغییر کاتالوگ، backup منطقی `pg_dump -Fc` در `/home/shahab/backups/t07/shahab-t07-20261022-r50QDp.dump` با دسترسی خصوصی ساخته شد. نسخهٔ محلی خصوصی در `%TEMP%/shahab-t07-20261022-r50QDp.dump` قرار دارد. اندازه هر دو ۱۱۹٬۲۳۸ بایت و SHA-256 هر دو `159c4708b307e4c4d95246b49a045a2c742403bf17f63d1d6a3f5364cb9d97ad` است. restore با `pg_restore --exit-on-error --no-owner --no-acl` در کانتینر موقت PostgreSQL 16 بدون شبکه موفق شد: revision بازگردانده‌شده `ff11b02f0001`، شمار نسخه‌های کاتالوگ صفر و شمار نشست‌های پرسشنامه ۲۰ بود. کانتینر موقت پس از آزمون حذف شد؛ backupها حفظ شدند. این آزمون بازیابی schema/data را اثبات می‌کند، اما بازسازی roleها و ACLهای production را اثبات نمی‌کند. پیش از عملیات نوشتنی آینده باید backup تازه گرفت و همین کنترل را تکرار کرد تا نوشتن‌های جدید کاربران از دست نروند.

پیش‌بررسی ابزار نشان داد روی سرور checkout شامل `scripts/operations_tool.py` وجود ندارد و `SHAHAB_OPERATIONS_AUTHORITY` و URL مستقل ابزار در تنظیمات production حاضر نیستند. این کمبود با استفاده از حساب runtime API، حذف احراز هویت، token ساختگی یا اجرای SQL مستقیم جبران نمی‌شود. کوچک‌ترین مسیر امن، اجرای همان checkout بازبینی‌شده با وابستگی‌های سازگار از محیط خصوصی و محدود روی زیرساخت موجود، اتصال فقط با نقش DB غیرمالک و اختصاصی ابزار، و تزریق authority موجودِ HTTPS با MFA و نقش‌های جداگانهٔ data-editor/admin از مسیر secret خصوصی است؛ ابزار در هر مرحله هویت و مجوز را دوباره بررسی می‌کند. تا آماده‌شدن این موارد، حتی با مجوز مالک، فرمان انتشار قابل اجرای امن نیست. ساخت ایمیج جدید صرفاً برای حضور اسکریپت در API لازم نیست.

**برنامهٔ مشخصِ مشروط به تأیید مستقل مالک:** مقصد PostgreSQL فعلی `shahab-prod` با revision `ff11b02f0001` است. source/config همان hash و نسخهٔ بالاست. کدهای یکتای پیشنهادی `t07-prod-official-598052635954-20261022` برای import و `t07-prod-official-598052635954-1.1.0` برای version هستند. از ریشهٔ checkout بازبینی‌شده و با فایل‌های JSON خصوصیِ بدون secret، هر مرحله با `python -m scripts.operations_tool --command /private/NN-stage.json` اجرا می‌شود: import و review و prepare با هویت data-editor، سپس پس از بررسی diff/audit، approve و publish با هویت admin. محتوای command مطابق `docs/operations/operations-runbook.md` فقط operation، کدهای بالا و دلیل مصوب را دارد؛ manifest دلخواه وارد ابزار نمی‌شود. پیش از هر فرمان، مقصد DB، head و grant تازه کنترل می‌شوند. پس از publish، read-only count=102، config فعال `1.1.0`، head، و پاسخ واقعی API همان نسخه بررسی می‌شود. خطای مبهم با اجرای دوبارهٔ کور ادامه نمی‌یابد.

بازگشت فوری به نسخهٔ منتشرشدهٔ قبلی ممکن نیست، چون کاتالوگ کنونی خالی است. اگر publish کامل و درست بود اما نتیجه نامطلوب شد، انتشار اصلاحیِ مصوب کم‌خطرتر از restore کور است. بازگردانی backup در production فقط با توقف مسیرهای نوشتن، backup تازهٔ وضعیت پس از انتشار، بررسی دادهٔ افزوده‌شدهٔ کاربران و مجوز جدا برای restore مجاز است؛ backup قدیمی را روی دادهٔ زنده بازنویسی نمی‌کنیم. در این مرحله هیچ import، publish، migration، restart یا restore روی production اجرا نشده است.

## آماده‌سازی مسیر SSH محلی، پیش از تأیید نهایی مالک

مالک اجرای SSH محلی به‌جای authority آماده‌نشده را خواست و سپس روشن کرد که فقط یک اپراتور واقعی دارد. بنابراین مسیر نهایی CLI در همین شاخه `--local-owner-operator` است: نشست SSH موجود root مالک، policy متعلق به root با actor واحد و دو نقش صریح editor/admin و expiry کوتاه، بازخوانی grant در هر فرمان، و همان `InternalDataOperations`، `ServingPublicationService`، audit و transaction قبلی. هر پنج مرحله جداگانه اجرا می‌شوند و actor هر دو نقش در audit یکسان است. این روش تأیید دو نفره یا MFA را اثبات نمی‌کند و کنترل مستقل به آینده موکول است؛ حساب/کلید صوری ساخته نمی‌شود. wrapper ثابتِ root-owned، checkout خواندنی و ایمیج API موجود، credential نقش محدود DB را فقط در کانتینر موقت روی شبکهٔ DB موجود تزریق می‌کند. API عمومی، auth مشتری، schema، scoring و runtime image تغییر نکردند. [دستورالعمل اجرایی](../operations/t07-local-ssh-publication.md) artifact، policy، command، grant محدود، ترتیب مراحل و بازگشت را مشخص می‌کند. هیچ حساب، grant، policy یا credential در production هنوز ساخته/تغییر داده نشده است.

آزمون‌های محلی: ۵ تست policy در کانتینر Linux شامل رد root بدون sudo، UID متفاوت، فایل قابل‌نوشتن و symlink پاس شدند؛ آزمون همان مسیر با PostgreSQL موقت، role محدود، رد publish برای editor و import برای admin، شکست تزریقی audit بدون انتشار، و publish موفق بعد از رفع خطا پاس شد. ابزار `ruff` و `git diff --check` پاس شدند. تلاش اول اجرای integration در Windows به‌خاطر نبود `openssl` در PATH fixture متوقف شد؛ با OpenSSL موجود Git و DB موقت تازه بازاجرا و پاس شد. این آزمون به‌معنای نصب/تأیید actorهای مستقل یا انتشار در production نیست.

پیش از عملیات اصلی، commit نهایی ابزار، source/config، مقصد و backup تازه باید در درخواست تأیید تجمیع‌شدهٔ مالک قرار گیرد. تصمیم اخیر مالک، الزام دو هویت مستقلِ عملیات داده را برای این تحویل حذف و ثبت محدودیت کنترل دو نفره را الزامی کرده است. مجوز پیشین برای طرح دوحسابی، نصب policy تک‌مالکِ اصلاح‌شده را به‌تنهایی تأیید نمی‌کند. توصیهٔ واقعی و جزئیات API هنوز آزموده نشده‌اند و T07 باز است.
