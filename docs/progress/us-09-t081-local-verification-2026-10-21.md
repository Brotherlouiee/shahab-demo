# US-09.T081 — آزمون واقعی API روی Docker محلی

**وضعیت: آزمون‌های محلی، شامل مسیر مثبت با fixture آزمایشی، اجرا شدند؛ پذیرش آنلاین و تسک کامل نیستند.** به دستور مالک، محیط آزمایشی فقط روی لپ‌تاپ در WSL/Docker است. هیچ محیط، حساب SSH، تونل، گواهی یا تنظیم تازه‌ای روی سرور ساخته نشد و production تغییر نکرد. authority عملیاتی انتشار داده/config آماده نیست؛ فقط پس از مجوز صریح بعدی مالک، fixture رسمی در PostgreSQL تازهٔ یک‌بارمصرف از مسیر محافظت‌شدهٔ تست منتشر شد.

> ادامهٔ همین PR در ۲۰۲۶-۱۰-۲۱: ابزار قابل بازاجرای `scripts/verify_t081_local.py` اضافه شد و روی همان API مستقل، پس از یک timeout گذرای challenge در اجرای اول، اجرای کامل با کد خروج صفر گذشت. درخواست challenge جداگانه ۲۰۰ در ۱٫۵۸ ثانیه داد؛ علت timeout اول اثبات نشد و به‌عنوان شکست محصول یا رفع قطعی معرفی نمی‌شود. ابزار هیچ شماره، cookie، token، پاسخ خام یا شناسهٔ خصوصی چاپ نمی‌کند. تست guard آن چهار حالتِ پروژهٔ درست، پروژهٔ دیگر، محیط production و bind عمومی را می‌سنجد. [فرمان و مرز اجرا](../runbook/api-testing.md).

## محیط و جداسازی

- پروژهٔ Compose محلی `shahab-t081-local` با API، PostgreSQL و Redis سالم اجرا شد. API فقط روی `127.0.0.1:8000` در دسترس است؛ این URL نشانی آنلاین دو آزمونگر نیست.
- volume تازهٔ `shahab-t081-local_postgres_data` از volume موجود `shahab-demo_postgres_data` جداست. پروژه و دادهٔ قبلی دست‌نخورده ماندند. migration دیتابیس تازه به `ff11b02f0001 (head)` رسید.
- تصویر API فقط در Docker محلی build شد؛ هیچ image منتشر یا روی سرور مستقر نشد. کاتالوگ و config منتشرشده در این دیتابیس وجود ندارند.
- شناسهٔ **تصویر در حال اجرای محلی** هنگام بازبینی `sha256:23065a4c97be32de8c3d0f7a87ec8b30f1d3dcadb5305f5c8ae36c780e4cfe64` بود؛ container و tag هر دو همین ID را نشان دادند. این شناسه digest رجیستری v0.1.0 نیست. مبنای کد runtime در شاخه، `main@14bef9c427b20198c36f1f4affe29c30d78918e9` است؛ commitهای بعدی PR فقط مستندات/ابزار آزمون را تغییر داده‌اند. تصویر پیش از ابزار جدید ساخته شده و ابزار روی میزبان اجرا شد؛ ادعای build تصویر از ابزار جدید نمی‌شود.
- Swagger محلی `/docs` و قرارداد `/api/v1/openapi.json` هر دو ۲۰۰ دادند. قرارداد ۱۷ عملیات محصول و دو health route، جمعاً ۱۹ مسیر، دارد.

## تعیین تکلیف داده و آزمون مثبت

`data/fixtures/recommendation-contract-fixtures.v1.json` fixture قرارداد است و کاتالوگ serving قابل انتشار نیست. تست‌های `backend/tests/test_t06_postgresql.py` و `backend/tests/test_t06_live_recommendation.py` مسیر مثبت را روی DB disposable با materializer می‌سنجند؛ این تست‌ها مجوز انتشار مستقیم برای دیتابیس API محلی نیستند. `backend/tests/test_operations_tool_postgresql.py` نیز TLS authority fixture و role محدود را فقط در integration test به‌کار می‌برد؛ fixtureِ `amr=mfa` گواه MFA واقعی اپراتور نیست.

مسیر عملیاتی همان `scripts.operations_tool` با import → review → prepare → approve → publish، authority introspection HTTPS معتبر، MFA واقعی انسان و نقش‌های جداگانه است؛ جزئیات در [protected-tool](../operations/protected-tool.md)، [operations-runbook](../operations/operations-runbook.md) و [import-runbook](../operations/import-runbook.md) آمده است. بازبینی خودکار ابتدا ساخت volume تازه و publish fixture را به‌دلیل منع قبلی مالک رد کرد؛ آن اقدام اجرا نشد. پس از **مجوز صریح جدید مالک** برای استثنای محدود PostgreSQL موقت لپ‌تاپ، آزمون بخش بعد اجرا شد. این مجوز authority عملیاتی، دادهٔ مصوب یا MFA واقعی را جایگزین نمی‌کند.

## آزمون مثبت با fixture محافظت‌شدهٔ موقت

مالک پس از منع اولیه، فقط برای PostgreSQL تازه و موقت روی لپ‌تاپ اجازهٔ import/publish fixture رسمی را صادر کرد. در اجرای دوم `python -m scripts.run_t081_fixture_test`، پروژهٔ جداگانهٔ `shahab-t081-fixture-f03ab061` با volume مستقل ساخته شد و پس از آزمون فقط container همان پروژه متوقف شد؛ volume برای بررسی باقی ماند. ابزار `scripts.operations_tool` با TLS authority آزمایشی، نقش محدود، و مراحل import → review → prepare → approve → publish استفاده شد. هیچ انتشار مستقیم materializer روی DB سرویس محلی یا production انجام نشد.

یک آزمون integration با PostgreSQL واقعی و دو `TestClient` مستقل پاس شد: ورود mock هر دو حساب، ساخت و پاسخ‌دهی ۱۰ سؤال، توصیهٔ موفق ۲۰۰ با config `1.1.0` و ۱۰۲ نتیجه، جزئیات وام ۲۰۰، ذخیره/فهرست/حذف نشان، فهرست/جزئیات/پنهان‌سازی تاریخچه، رد دسترسی حساب دوم به نشست و سابقهٔ حساب اول با ۴۰۳/۴۰۴، حفظ ردیف پنهان‌شده در DB، و بازیابی نشست پس از ساخت دوبارهٔ app. زمان اجرای تست ۸۲٫۶۷۱ ثانیه بود. خروجی به جز status و timing توسعه شامل شناسه، شماره، cookie یا پاسخ خام نیست. اجرای نخست، خود آزمون را پاس کرد ولی teardown قدیمی هنگام downgrade دیتابیس موقت خطا داد؛ اجرای دوم با نگه‌داشتن schema همان volume موقت به‌جای downgrade با `OK` پایان یافت. نخستین اجرای CI نیز همین خطای teardown را نشان داد؛ guard اکنون بر اساس اجرای همین تست در کلاس فعال می‌شود تا هم در runner محلی و هم CI دیتابیس یک‌بارمصرف حفظ شود، بدون تغییر رفتار teardown آزمون‌های دیگر.

پس از اصلاح teardown، اجرای سوم روی پروژهٔ تازهٔ `shahab-t081-fixture-c047c13e` نیز در ۶۳٫۷۴۲ ثانیه با `OK` پاس شد و container فقط همان پروژه متوقف شد. این شاهد، آزمون **با داده و احراز هویت آزمایشی** است؛ تأیید دادهٔ مصوب عملیاتی، MFA واقعی، مالکیت شماره، ارسال SMS یا آزمون HTTPS آنلاین دو شخص نیست. دیتابیس API روی `127.0.0.1:8000` همچنان کاتالوگ خالی دارد و ۵۰۳ آن تغییر نکرده است.

## موارد باز

پذیرش آنلاین T081 مسدود است، چون مالک محیط را به لپ‌تاپ محدود کرده و دسترسی محدود مستقل برای آزمونگر دوم آنلاین وجود ندارد. انتشار داده/config **مصوب عملیاتی** نیز به authority محافظت‌شده و نقش‌های لازم وابسته است که فعلاً آماده نیست. مسیر مثبت، history و bookmark در fixture تستی شاهد دارند، ولی همان مسیرها روی API آنلاین محدود با دو شخص، دادهٔ عملیاتی و HTTPS هنوز اجرا نشده‌اند. OTP واقعی و مالکیت شماره نیز تا تأیید الگو و مجوز ارسال آزموده نمی‌شوند. CI یا سالم‌بودن کانتینر این خلا را پر نمی‌کند. **US-09.T081 باز می‌ماند.**

## اصلاح teardown و آزمون HTTP کانتینری در ادامهٔ PR #149

علت واقعی شکست teardown، guard مهاجرت `ff11b02f0001` بود: API نشان را منطقی حذف می‌کند و رکورد `account_bookmarks` باقی می‌ماند؛ guard با وجود هر رکورد نشان، downgrade مخرب را رد می‌کند. اکنون همان تست پس از تمام assertionهای ماندگاری فقط رکورد نشان متعلق به fixture خود را پاک می‌کند و `tearDownClass` همیشه downgrade را اجرا می‌کند. اجرای تازهٔ `python -m scripts.run_t081_fixture_test` روی PostgreSQL مستقل با downgrade واقعی در ۱۱۴٫۰۶۲ ثانیه و `OK` پاس شد. توضیح قدیمی بالا دربارهٔ guard شرطی، وضعیت فعلی کد نیست.

فرمان `python -m scripts.run_t081_fixture_test --container-http` در پروژهٔ مستقل `shahab-t081-fixture-3211cc65` موفق شد. مهاجرت تا head، انتشار fixture رسمی از مسیر import → review → prepare → approve → publish با authority آزمایشی TLS و نقش محدود، و ۱۰۲ نسخهٔ وام/config `1.1.0` تأیید شد. همهٔ درخواست‌ها با HTTP واقعی به کانتینر API روی `127.0.0.1:58001` رفتند؛ تصویر محلی این اجرا `sha256:bce4c2c8fddbb50e7da838eca7d12029886a808aa633a86669ac765860de1f44` است و در رجیستری منتشر نشد.

دو حساب مصنوعی با cookie jar جدا ورود mock، پروفایل، پرسشنامه و ۱۰ پاسخ، توصیهٔ ۲۰۰ و جزئیات وام را گذراندند. تاریخچه و نشان پیش از restart **غیرخالی** بودند؛ فقط API همان پروژه restart شد و هر دو نشست معتبر، پروفایل، پرسشنامه، تاریخچه و نشان دوباره خوانده شدند. حساب دوم به نشست/سابقهٔ حساب اول دسترسی نداشت؛ hide و remove پاسخ ۲۰۴ دادند و ردیف‌های `hidden_at` و `removed_at` در DB حفظ شدند. ورودی نامعتبر ۴۲۲، توصیهٔ ناقص ۴۲۲، پرسشنامهٔ منقضی ۴۱۰، نشست منقضی ۴۰۱ و خروج ۲۰۴/۴۰۱ ثبت شدند. یک درخواست توصیه ۷۲۶۴ میلی‌ثانیه طول کشید؛ نمونهٔ واحد است. خروجی ابزار فقط نام عملیات، status، شناسهٔ image و مدت را چاپ کرد. volume آزمایشی باقی ماند و همهٔ سرویس‌های همان پروژه با profile صحیح متوقف شدند؛ پروژه‌های دیگر تغییر نکردند.

NetBird روی لپ‌تاپ متصل است، ولی هنگام بررسی peer متصل دیگری نداشت. API mock همچنان فقط loopback است و HTTPS خصوصی و آزمون دستی دو شخص اثبات نشده‌اند. این شاهد با داده/احراز هویت آزمایشی، تأیید دادهٔ عملیاتی، MFA واقعی یا مالکیت شمارهٔ تلفن نیست. معیار پذیرش آنلاین T081 همچنان باز است.
